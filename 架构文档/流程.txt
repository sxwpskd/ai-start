# 一、核心状态机与通道矩阵
======================================================================

## 1.1 阶段状态机

```
[BASE（构思期）] ──点击"生成代码"──> [HTML / MULTI_FILE / VUE_PROJECT（生成期）]
   │ 多轮构思对话                      │ 多轮改码对话（现有行为，不动）
   └── 状态单向；回构思需重置（暂不做）
```

说明：上图为用户体感（产品视角）。实现视角：BASE 与 HTML/MULTI_FILE/VUE_PROJECT
为四种等价模式、统一主流程分流，代码中无任何"期"的基础设施——阶段感由
codeGenType 值 + 成功后落库时机 + 前端按钮显隐涌现（开发文档.txt 决策记录第 16 条）。

## 1.2 通道矩阵（目标）

| 请求场景 | 工作流开关 = 开 | 工作流开关 = 关（直连） |
|---|---|---|
| BASE 期构思对话 | base 工作流（rag 占位 → think 节点），同步阻塞返回【B6 已编码待联调】 | 流式输出 + AI 自主调用 writeThink / readThink 工具【已实现（B4）】 |
| 点击"生成代码" | 生成图（AI 路由 → rag → 读 think → 生成 → 质检重试 → 构建），SSE 进度推送【B7 后端已编码待联调；前端接线未做】 | 用户手选 CodeType → update → 现有生成分支【已实现（B5）】 |
| 生成后改码对话 | 始终直连流式（现有行为，不进图） | 同左 |

两通道共同产物链：writeThink 全量覆盖写 think_{appId}.md（工具内同步渲染
index.html）→ tmp/code_output/base_{appId}/ 目录 → 前端预览浏览器展示

说明：
- 直连模式下 BASE 期的工具调用流式事件已有基础设施（VUE_PROJECT 模式 +
  覆盖的 TokenStream 源码已支持工具调用事件流），改动最小
- 工作流模式下 BASE 期同步阻塞：用户发消息 → 等 rag+think 跑完 → 一次性返回 +
  预览刷新（构思阶段耗时约几十秒，可接受）
- 生成图模式下同步阻塞耗时可能数分钟（含 npm 构建），需超时配置保障
  （已定：Nginx 600s + 前端 10min + 生成中防重，见 开发文档.txt 决策记录第 8 条）

# 二、【现有】流程实录（当前代码库真实行为）

## 2.1 应用生命周期

```
[创建] --多轮对话生码--> [代码已生成] --部署--> [已部署]
  +--任意状态可删除(级联删除对话历史)
```

两个关键代码事实（低风险重构依据）：
- 事实1：创建时 AI 路由结果只 log 未落库（AppServiceImpl.createApp）——"创建时定
  codeGenType"实际未生效，挪到点击"生成代码"时处理属于修复隐患
- 事实2：工厂 createAiCodeGeneratorService 的 switch 无 BASE 分支（会抛不支持），
  Facade/Parser/Saver 的 BASE 分支走不通——BASE 是半死代码，可安全重定义

## 2.2 对话生成代码（GET /app/chat/gen/code，SSE）

```
用户消息 → AppController（登录校验 + @RateLimit USER 5次/60s）
  → AppServiceImpl.chatToGenCode（仅创建者）
  → chatHistoryService.addChatMessage（USER 消息落库）
  → AiCodeGeneratorFacade.generateAndSaveCodeStream
      → 工厂：Caffeine 缓存 (appId+codeGenType)；创建时 Redis 记忆(窗口20) + DB 回灌
        （VUE_PROJECT：prototype 多例模型 + ToolManager 工具 + 防幻觉策略）
      → 流式响应：
          - HTML/MULTI_FILE：Flux 直出；完成后聚合 → 解析 → 保存
          - VUE_PROJECT：TokenStream，AI 调文件工具写项目；完成后 npm 构建
  → StreamHandlerExecutor（AI 响应落库）→ 前端 done 事件
```

SSE 消息协议（VUE_PROJECT / BASE，2026-09-18 补）：TokenStream 三回调各转一种
JSON 消息（ai/model/message 包，type 字段判别）——onPartialResponse → ai_response
（文本片段）；onPartialToolExecutionRequest → tool_request（id/name/arguments）；
onToolExecuted → tool_executed（id/name/arguments/result）→
JsonMessageStreamHandler 按 type 分发：AI 文本拼接透传；工具请求按 toolId 去重后
经 BaseTool.generateToolRequestResponse 格式化；工具结果经
generateToolExecutedResult 格式化并揉入 AI 消息落库 → Controller 包装
{"d": chunk} → 前端 EventSource 消费。HTML / MULTI_FILE 无此层：Flux 纯文本
直出，SimpleTextStreamHandler 只做聚合落库。

## 2.3 对话记忆（双轨）

写：消息 → DB chat_history（全量）+ ChatMemory（Redis，窗口20）
读：创建 AiService 时 DB 最近 N 条按时间正序回灌；隔离：memoryId = appId

## 2.4 部署 / 预览 / 下载

```
部署：deployApp → 6位 deployKey → VUE 则构建 dist → 复制到 tmp/code_deploy/{deployKey}
      → 更新库 → 返回 URL → 虚拟线程异步截图 → COS → 更新 cover
预览：StaticResourceController → tmp/code_output/{deployKey}/**（.txt 返回 octet-stream）
下载：/app/download/{appId} → ZIP 文件流
```

## 2.5 LangGraph 演示工作流（/workflow/*，独立链路，未接主业务）

## 2.6 构思工作流通道（B6，2026-09-19 编码完成，联调验收待做）

```
用户消息（开关=开且 BASE 期，含预览页点选元素转文字）
  → POST /app/chat/think/workflow {appId, message}
  → AppServiceImpl.thinkWorkflow：参数校验 → 仅创建者鉴权 → codeGenType
    空值兜底 BASE / 非 BASE 拒绝 → 先落用户消息（时序硬约束：记忆回灌的
    limit(1, maxCount) 靠"跳过最新一条"排除本轮消息，决策记录第 20 条）
  → BaseWorkflowExecutor（@Component，虚拟线程 + Future.get(10min) 超时）

  → 前端 sendMessageByWorkflow 回填消息 + previewKey++ 强制重建预览 iframe

## 2.7 生成工作流通道（B7，2026-09-19 后端编码完成，前端接线与联调验收待做）

```
用户触发生成（开关=开；按钮固定文案 / 前端口令识别 / 直创应用初始需求）
  → GET /app/gen/workflow?appId=&message=（SSE，SseEmitter(0L) 立即返回）
  → AppServiceImpl.genWorkflow 同步段（请求线程）：参数校验 → 仅创建者鉴权 →

    business-error 事件）
  → GenWorkflowExecutor.submit（虚拟线程；加锁与解锁必须同线程，决策记录第 27 条）：
      tryLock(gen_workflow:lock:{appId}) 不等待，失败抛"应用正在生成中"
      ①先落用户消息（时序硬约束同 2.6，决策记录第 20 条）
      ②existsThink 为真则 readThink 入 context.thinkContext（不存在置空不拼）
      ③初始上下文：originalPrompt = App.initPrompt（路由依据，决策记录第 25 条）
      ④CodeGenConcurrentWorkflow.executeWorkflow(context, stepCallback)：
        image_plan → 4 并发搜集 → aggregator → prompt_enhancer → router
        （生成期应用跳过 AI 路由直接用锁定类型；null/BASE 兜底 HTML；结果只写
        context 不碰 DB）→ rag（占位）→ code_generator（appId 取 context、
        thinkContext 拼增强提示词、流聚合进 genReply——VUE 经
        collectHistoryText 复用直连落库规则）→ 质检条件边（fail 回
        code_generator 带修复提示词 / VUE 走 build / 其他 skip）→ project_builder
      ⑤全图成功后统一落库：codeGenType = generationType（单向锁定）+

配套端点：GET /app/think/exists?appId=（构思文档存在性预检：无 think 文件时

# 五、关键数据实体
======================================================================

## 5.1 既有数据模型（2026-09-18 补 · 状态机与数据流的物理真相）

- App.codeGenType（varchar）：阶段状态机的唯一物理载体——无状态表、无状态框架，
  单字段 + 成功后落库时机 + 前端按钮显隐涌现阶段感（决策记录第 16 条的数据层
  印证）；BASE 枚举值已存在，无需迁移
- ChatHistory（chat_history 表）：无模式差别的统一对话账本——无 codeGenType 列，
  构思/生成/改码对话同表流水，仅 user/ai 两类消息，appId 串联全流程；
  工厂回灌记忆按 appId 取最近 N 条（模式无关，等价模式的又一印证）；
  工具调用事件无独立记录类型——经 BaseTool.generateToolExecutedResult 格式化
  为文本揉进 AI 消息落库

  零改动的原因
